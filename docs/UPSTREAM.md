## Is a rebase due?

```bash
scripts/check_upstream.py
```

compares `UPSTREAM_PIN` with the newest Mac Stable on chromiumdash (exit 1
when behind). Exit 0 requires both the version and Chromium commit to match
the Mac Stable response. Exit 2 means the check is unconfirmed: the pin is
ahead, the commits differ, the response is invalid, or the request failed.
An ahead pin is not treated as Stable or as a request to downgrade. `--json`
includes `status`, both commits and `rebase_due`; an unsuccessful fetch or
validation reports `status: "error"` and `rebase_due: null`. Automation
should check the exit status as well. Run it before every release.

`scripts/verify_patches.sh` downloads exactly the patched upstream files at
the pinned tag and applies every patch in order with `git apply --check` and
`git apply`. That proves the series applies; compiling and running are
separate checks.

## Rebase procedure

This updates the Chromium checkout to a new tag and reapplies the series;
it is not a `git rebase` of this repository. Run each step in order and
stop at the first failure. Sync and a full build can take hours, so keep
the Mac plugged in, and never run two builds against one output directory.

1. Pick the new Mac Stable tag from chromiumdash and verify the series before
   changing the pin: `TAG=<new> scripts/verify_patches.sh`. A failure means a
   patch needs refreshing against that tag; keep it minimal. Patch 0007 is
   generated: regenerate it with `scripts/rebrand_strings.py --patch` rather
   than rebasing it.
2. In `~/chromium/src`, check `git status`: expect the tracked changes
   Merlin's patches made and the overlay's untracked symlinks. Keep the
   tracked changes in a named stash (never `git reset --hard` or
   `git clean`), then move to the tag and sync:

   ```bash
   git stash push -m "before Merlin Chromium update to <new>"
   git fetch --depth=1 origin refs/tags/<new>:refs/tags/<new>
   git checkout --detach refs/tags/<new>
   caffeinate gclient sync -D
   ```

   Do not pop the stash onto the new source: it holds the old applied
   patches. Keep it for recovery.
3. Write the tag, the checkout's `git rev-parse HEAD` and today's date to
   `UPSTREAM_PIN`. From this repository run `scripts/apply_overlay.sh`
   (which applies the series) and `scripts/check.sh`. In the checkout:

   ```bash
   gn gen out/Modal
   gn check out/Modal '//chrome/browser/ui/modal_browser/*'
   caffeinate autoninja -C out/Modal -j 4 chrome browser_tests
   ```

   Save the first real compiler error; API changes need overlay changes,
   which rebuilding alone won't fix. If Rust or FFI compilation fails,
   compare the vendored `cxx` version with the Cargo pin.
4. Re-read the APIs in [ARCHITECTURE.md](ARCHITECTURE.md) ("Chromium entry points used") and
   the `BrowserWindow` overrides in `merlin_react_window_mac.mm`: upstream
   adds and removes `BrowserWindow` methods often, and `OpenGURL` is marked
   for removal.
5. Run `scripts/check.sh`, then the ad-blocker suite
   (`scripts/run_browser_tests.sh`) and the upstream suites
   (`scripts/run_browser_tests.sh 'BrowserViewTest.*:BrowserCommandsTest.*:BrowserCommandControllerBrowserTest.*'`,
   then `scripts/run_browser_tests.sh 'FindInPageControllerTest.*'`). The
   runner adds `--modal-browser-upstream-defaults` for upstream suites.
6. Build the release engine (`scripts/build_release.sh`), rebuild the React
   host (`scripts/build_react_shell.sh`), assemble them
   (`apps/browser/README.md`) and run `scripts/run_e2e_tests.sh` against the
   assembled app. Then work through the release checklist in
   `apps/browser/README.md` for what the end-to-end tests can't see.
7. Record the build and results, then commit the pin, patch and API
   refreshes and the documentation as "Rebase onto <version>".

Follow Stable, not `main`: Stable is what receives security fixes.

## Security responsibility

* Track Chrome Stable releases and their security notes. Target: a rebased,
  tested release within 3 days of a Stable security release, within 24 hours
  when Google marks a fix as exploited in the wild. `scripts/check_upstream.py`
  detects them; people get the release through Homebrew or the download.
* Keep security-sensitive changes minimal. The native blocker needs explicit
  `//content` and `//third_party/blink` hooks for worker responses, document
  lifecycle and memory-cache policy (0014–0031, 0046). Do not weaken sandbox,
  network security or permission checks; keep each hook covered by native
  tests and repeat them after every Chromium update.
* Never ship with sandbox, site isolation, interstitials or permission checks
  weakened. Safe Browsing lookups need a Google API key that forks don't
  have, so they do not run (see the release notes' limitations).
* Own branding and bundle ID; no Google Chrome trademarks or assets. Both
  build configs set `branding_file_path` to Merlin's `BRANDING`, with
  proprietary codecs and without Widevine (DRM sites open in WebKit).
* Release policy: GitHub Releases without Developer ID signing or Apple
  notarization; neither is a release blocker ([RELEASE.md](RELEASE.md)).
